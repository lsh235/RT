# v1.16.0-rc.1 (R11) acceptance — public installation and contributor readiness

Status: **Scope fixed; implementation in progress**
Date: 2026-10-19
Branch: `codex/oss-readiness-v1-16`
Baseline: annotated `v1.15.0` at `3ad25c13bb0cf6334a1bf36a6b54c841ce2c8c58`

## User outcome

An external Elasticsearch/RAG developer can understand the tested support boundary, install the workbench from source or the provided local Compose setup, preserve or restore local state, and contribute or report a security issue using clear Korean and English guidance. The distribution inventory distinguishes project code, dependencies, optional model assets, and third-party sample content. This RC does not claim general retrieval quality, production deployment readiness, or rights to redistribute third-party records without evidence.

## Fixed work packages (maximum six)

1. **License and asset audit:** verify Apache-2.0 metadata and license file; inventory exact Python and browser runtime/development dependency trees and their declared licenses/notices; inspect packaged artifacts; record model/tokenizer download boundaries; determine the provenance and redistribution basis for both bundled gRPC Jira data files. A hosting URL or the code license is not permission evidence. No new third-party sample, qrels, or source documents may be added.
2. **Support matrix:** document Python, Node/browser, operating system, Docker/Compose, and Elasticsearch versions with separate labels for CI-tested, independently exercised, and unverified combinations. Do not claim support beyond recorded evidence.
3. **Loopback container setup:** provide a pinned, reproducible Docker image and Compose example for the workbench plus a disposable local Elasticsearch node. Host-published ports must bind to `127.0.0.1`; allow port overrides for isolated validation; never require stopping or replacing an existing service. Security-disabled Elasticsearch is only for loopback development. Compose data lives in named volumes and bootstrap remains explicit.
4. **Install, upgrade, migration, and recovery guidance:** add Korean and English steps for source install, optional extras, Compose, upgrading from the prior release, database migrations, backup/restore and integrity checks, rollback limitations, and Elasticsearch/vector compatibility boundaries. Documentation must match implemented commands and migration behavior.
5. **Security and contributor guidance:** add Korean and English security reporting and contribution workflows; explain loopback-only local account boundaries, shared-index credentials, local data locations, model downloads, optional provider data flow, dependency updates, and test evidence limits. Update the changelog for the RC without a quality claim.
6. **Independent release QA:** a validator who did not implement the relevant changes runs the package, lockfile, supported-runtime, browser, disposable-ES, Compose, migration/restore, documentation-link, and preservation checks; inspects produced artifact contents and the sample-rights record; writes a separate QA report.

## Evidence boundaries

- The source code license does not automatically license third-party issue text, mappings, sample data, dependencies, model weights, or tokenizer files.
- The existing 25-document Jira sample remains a regression fixture only. It cannot close a sourced-quality gate or support a general retrieval-quality claim.
- A Docker/Compose smoke validates the documented loopback development path only. It does not establish production hardening, multi-tenant isolation, or public-network suitability.
- Upgrade and SQLite restore evidence covers the tested local per-file path; it does not claim an atomic backup across Elasticsearch and all local databases.
- The inherited representative sourced-quality gate is not part of R11 implementation acceptance and remains open for R12.

## Retry and release rule

R11 receives one initial implementation round and at most three fix/retest rounds. It starts at global round 33; the fixed plan allows 48 total rounds. The independent QA report determines evidence status, while the coordinator assigns final PASS/FAIL/NOT RUN. An unresolved required gate prevents the `v1.16.0-rc.1` tag and cannot be silently waived. R12 is the fixed final closure stage; any still-missing required external evidence must be recorded as NO-GO, not converted to PASS.
