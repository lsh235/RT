## Fixed scope

Add a safe, repeatable file-import path to the existing private knowledge store. Keep all documents, judgments, source metadata, and quotas inside the authenticated account's state database. Shared Elasticsearch indexes remain a separate path. File contents are untrusted data and must be parsed as text; never execute markup, scripts, formulas, or embedded instructions.

- Import `.txt`, `.md`, `.csv`, and `.jsonl`; CSV/JSONL users select title, content, and optional source fields.
- Strictly decode UTF-8, preview parsed records, report file/row errors, and let valid rows succeed with explicit partial-success results.
- Record a stable document ID, revision, source name/record identity, and cryptographic hashes for source and document content.
- Preview duplicates before mutation. Require an explicit `skip` or `replace` choice for each duplicate; repeated identical import must be deterministic.
- Let users edit/delete imported documents and show that private Elasticsearch state is stale until an explicit successful sync.
- Show per-account document and byte usage alongside the existing limits: 100 documents, 20 MiB total stored content, 1 MiB per document/import file. Bound rows/files per request and reject over-limit input before mutation.
- Export and restore the account's documents and private relevance judgments with provenance and document identity. Restore previews conflicts and requires explicit choices; restore never accepts an owner/account override and contains no authentication secrets.

### Coordinated API shape

Backend and browser implementation use these internal contracts; additive response fields are fine, but field names/status values stay aligned:

- `POST /api/knowledge/import/preview` payload: `filename`, `content_base64`, and optional `fields` (`title`, required `content`, optional `source`). Response: `file_sha256`, `format`, `fields_available`, `valid_records` (each with 1-based `row_number`, normalized `title`, `content`, `source_label`, `content_sha256`, and optional `duplicate` with `document_id`/`revision`), `errors` (optional `row_number`, stable `code`, safe `message`), `usage`, and `limits`. It must not mutate data. The first CSV/JSONL preview without `fields.content` returns available column/key names and `needs_field_mapping: true`; it does not report missing mapping as row parse errors. After the user selects fields, the browser repeats preview with the mapping. TXT/MD preview does not require field mapping.
- `POST /api/knowledge/import/commit` uses the same source/mapping plus `duplicate_actions: [{row_number, action: "skip"|"replace"}]`. Response `outcomes` use `created|replaced|skipped|unchanged|failed`, include row/document identity where applicable, and provide `partial`, `usage`, and private ES state. New records may be created without an action; every duplicate requires an explicit action.
- `POST /api/knowledge/export` returns `{format, version, created_at, documents, judgments}` with document IDs/content/provenance/revisions. It contains no credentials, local filesystem paths, or unrelated account identifiers.
- `POST /api/knowledge/restore/preview` accepts `{archive}` and validates version, hashes, limits, references, and conflicts without mutation. It returns a deterministic `archive_sha256`, row errors, duplicates, and quota impact. `POST /api/knowledge/restore/commit` accepts `{archive, expected_sha256, actions}` and rejects changed archives; conflict choices are explicit `skip|replace` per document. It reports per-document and per-judgment outcomes.
- Any raised JSON request-size allowance applies only to authenticated restore routes and is bounded by the 20 MiB account content limit plus a small serialization overhead. Ordinary API requests retain their 2 MiB cap.

Do not trust owner IDs, account IDs, file paths, or target aliases from request payloads. Derive the account scope from the authenticated server session. Import parsing must not follow paths supplied in a CSV/JSONL field. Treat Markdown, HTML-looking text, formulas, and embedded commands as inert content.

R04 adds account-scoped TXT/Markdown/CSV/JSONL import preview and commit, provenance hashes, deterministic duplicate handling, revisions, document editing/deletion, usage limits, and document/judgment export and restore. State migration v2 adds provenance/revision columns while retaining transactional, backed-up migration behavior. Private documents, chunks, FTS rows, judgments, and ES sync state remain in each authenticated account's state SQLite database. Save, import, and delete mark the private ES generation stale; a separate explicit sync stages and swaps only the authenticated owner's private alias. SQLite first-open setup is serialized by resolved database path before opening the file, followed by the shared WAL/migration lock.

The round-1 QA report directly rechecked authentication, CSRF/Origin, owner-bound private CRUD/search, import/restore field forgery, strict input bounds, account quotas, migration rollback, repeatable first-open behavior, and the shared/private search boundary. The restore request-size exception remains route-scoped; ordinary API requests retain the 2 MiB cap.

The implementation is limited to account-scoped local ingestion and lifecycle. It does not establish production multi-tenant security, add arbitrary shared-index mutation, or prove representative retrieval quality.
