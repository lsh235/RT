## User problem and fixed scope

Users can already run BM25, dense vector, and reciprocal-rank fusion (RRF), but the workbench does not provide one consistent way to compare candidate depth, final top-K, field boosts, per-lane ranks/scores, and an optional local reranker. R07 makes the compared request settings and result provenance inspectable while keeping Elasticsearch filters, concrete document identity, and account-private boundaries intact.

R07 adds one optional local cross-encoder: `BAAI/bge-reranker-v2-m3`, pinned to repository revision `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`. Its model page identifies the model as multilingual, lists Apache-2.0, documents a `sentence-transformers.CrossEncoder` usage path, and currently lists repository size as 2.29 GB. Sentence Transformers documents `CrossEncoder` revision pinning and `local_files_only`, which lets search use only a model that was explicitly prepared and cached. The download is large and is never part of normal BM25/vector/hybrid search. References: [official BAAI model card](https://huggingface.co/BAAI/bge-reranker-v2-m3/tree/953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e), [Sentence Transformers CrossEncoder API](https://www.sbert.net/docs/package_reference/cross_encoder/model.html).

The optional model is an integration candidate. R07 does not claim Korean retrieval quality, reranker superiority, or a measured quality improvement. Those claims require the judged-corpus gates in R08–R12.

## Fixed behavior and API boundaries

- Search modes remain `bm25`, `vector`, and `hybrid`. Each uses the same selected index, authenticated account scope, supported metadata filters, and selected embedding profile where vector retrieval is requested.
- `size` remains the final top-K for API compatibility (1–50; default 10). `candidate_pool` is independently bounded to `top_k..200`; omitted API values default to `top_k`. The browser defaults the pool to 50 and never below the selected top-K. Every active lane fetches this pool before the final top-K is selected. Hybrid search records `rank_constant` (1–200); field boosts and all effective limits appear in returned query settings. Out-of-range or malformed values fail explicitly instead of being silently clamped.
- Result provenance records each contributing lane's concrete `(index, id)`, original rank, and raw score. RRF retains per-lane rank/score evidence and reports its fused rank/score separately. Aliased indices with the same document ID remain distinct unless both concrete index and ID match. Nested comments/highlights remain attached to the lexical result.
- An optional `rerank` request applies the pinned local cross-encoder to the bounded retrieved candidate pool. The result reports pre/post rank, raw reranker scalar, model/revision/runtime, effective maximum input length, and elapsed inference time. None of these scores is represented as a relevance probability.
- `GET /api/reranker/status` reports safe runtime/cache/model readiness. `POST /api/reranker/prepare` requires explicit user consent before downloading model files. Search never downloads a missing model; an explicitly requested but unavailable reranker returns an actionable failure instead of silently changing modes. BM25, vector, and hybrid continue to work when the optional reranker extra is absent, provided their own requirements are met.
- Empty candidate sets are returned as empty results without loading the reranker. Mapping, model, Elasticsearch, authentication, and filter failures remain distinguishable from a valid empty result.
- Reranker scoring uses the model's raw scalar with an identity activation and a fixed maximum pair length. The response identifies this as an uncalibrated model score, not a probability. Candidate input truncation, if any, is explicitly reported.

## Bounded validation cases

Use synthetic task-owned Elasticsearch documents containing one Korean issue, one English issue, and one code-identifier issue. Include a small alias with two concrete targets that deliberately reuse a document ID, plus a nested comment field and a metadata field used by a filter. Run each search mode with the same query/filter and compare request/query metadata and result provenance. This validates interface consistency and isolation; it is not a relevance benchmark.

Run the reranker with three deterministic query/candidate pairs through the actual pinned local model. Validate execution and evidence fields, not that its ordering is superior to the original search. Also verify the disabled and missing-runtime paths, explicit preparation/download-consent path, explicit failure behavior, and no-model-load behavior for a valid empty result.
