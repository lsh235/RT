## Fixed scope

Incrementally separate HTTP route dispatch, feature services, local storage/migrations, evaluation helpers, and browser modules while preserving the existing API and local-first behavior. Keep the existing `auth`, `concepts`, `knowledge`, `evaluation`, `retrieval`, and `es_client` domain boundaries where they already work. Do not replace the server/framework or rewrite the frontend wholesale.

Required implementation:

- Move route registration/dispatch behind a dedicated API route boundary. Keep loopback/Host checks, cookies, authentication, CSRF, and authenticated owner scope enforced at the HTTP boundary before protected handlers run.
- Consolidate shared connection, index, and request validation paths where duplicate implementations currently diverge; preserve accepted input and response behavior.
- Establish a shared API error representation with stable machine-readable codes and user-facing messages. Preserve existing status codes and the existing `error` message field for current clients; do not expose stack traces, filesystem paths, SQLite details, credentials, or submitted private content.
- Replace implicit first-use DDL and scattered `ALTER TABLE` checks with explicit, per-database, versioned migrations for the control/primary database and secondary-account state databases. Recognize current legacy schemas, preserve saved rows and ownership markers, and fail closed on malformed/unknown schemas.
- Add a local maintenance backup/restore path for SQLite application data. Use SQLite-consistent snapshots that include WAL state, validate backups before restore, keep file permissions restrictive, constrain destinations to explicit operator-selected local paths, and document that the app must be stopped for restore. Elasticsearch indexes are outside this SQLite backup boundary.
- Extract the browser API client and at least one independent UI responsibility into ES modules; keep `app.js` as a small bootstrap/orchestration entry. Continue serving only explicit local static assets.
- Document API request/response/error contracts and the updated module/storage map.

## Execution and decision record

The baseline architecture map is in `docs/architecture/overview.md`. Source inspection identifies lazy schema setup in `auth.py`, `concepts.py`, and `knowledge.py`; account state shares the base SQLite file for the primary account and uses a UUID-named file for each secondary account. The independent R02 planning scout confirmed these boundaries without opening a database. The codebase-memory graph remains unavailable; use source inspection and report that limit.

The selected browser extraction seam is the Cycle 44 positive-target-miss feature currently grouped in `web/app.js`: scope fingerprinting, stale-report invalidation, miss rendering, and manual handoff. Keep `app.js` as a classic-script bootstrap and dynamically load the feature module before authenticated initialization; this preserves existing browser fixtures that inspect bootstrap globals. The implementation worker selected `web/api-client.js` and `web/cycle44-positive-target-misses.js`, served as `/api-client.js` and `/cycle44-positive-target-misses.js` from the explicit static allowlist. The API client should use a dependency-injected factory to avoid global state coupling.

Storage boundary: the base SQLite file holds both control/auth data and the primary account's application state. Secondary account states are separate UUID-named SQLite files; knowledge documents, chunks, FTS, and sync/vector data live in the owning account state file. Track schema versions per database file. The R02 maintenance commands operate on one explicit SQLite file at a time; operators back up the base and each secondary account file separately. This gives a SQLite-consistent snapshot per file, not a cross-file point-in-time transaction. Verify integrity and schema before restore; exclude Elasticsearch indices.
