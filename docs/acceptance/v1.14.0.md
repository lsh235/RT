## Goal and boundary

Make the existing concept tuner bounded, deterministic, and safe for local search experiments. Candidate search must use only `train`; candidate selection must use `validation`; no tuning path may read or expose a `test` split. Keep the saved baseline when validation is absent or no candidate is at least as good under the fixed comparison rule. Expose query-level known-relevant miss diagnostics with explicit limits.

R09 implements the R09 row in the [fixed OSS readiness plan](../roadmap/oss-readiness-plan.md) and closes the applicable Cycle 47 reproducible-tuning and Cycle 48 diagnosis requirements in [Cycle 45–48 roadmap](../cycle45-48-roadmap.md). R08's versioned qrels/test-once workflow remains the final sourced-quality evaluation path. No R08 test data is used for tuning or candidate selection.

This work remains a local search-quality workbench. It does not automatically modify production settings, establish general retrieval quality, or claim that tuning improves arbitrary corpora. The existing 25-document Jira sample remains regression-only. Synthetic and mock evidence can verify bounded behavior and diagnostics but cannot close the carried R12 sourced-quality gate.

## Fixed behavior

- A tuning request accepts `max_candidates` (positive; default 30; maximum 30, including the baseline) and `time_budget_seconds` (positive; default 600; maximum 600). Invalid or larger values fail before Elasticsearch search. The response's `tuning_budget` records both effective limits, `candidates_evaluated`, `elapsed_ms`, and `stop_reason` (`completed`, `candidate_budget`, or `time_budget`).
- Candidate enumeration and tie-breaking are deterministic for the same saved concept, train judgments, index/mapping identity, and fixed tuning algorithm. No hidden random seed or wall-clock input may alter candidate order or selection. Repeated-run IDs and timestamps may differ; the candidate trace, chosen configuration, and metric/output fingerprints must match when the inputs do.
- The finite candidate configurations are enumerated deterministically from the saved baseline. Candidate evaluation metrics use only current, non-stale `train` judgments; validation judgments are used only to select among the baseline and bounded configurations. Tuning must not inspect a test split or leak held-out metrics. If validation has no usable positive judgments, retain the baseline and record a specific reason.
- Select by the documented validation ordering: higher macro judged-only nDCG@K first, then higher judged coverage@K. If a candidate is worse on that ordering, retain the baseline. Exact ties retain the baseline. Missing/failed validation must never cause a candidate to replace the baseline.
- Saved run snapshots include the exact concept/query/judgment/configuration fingerprints, train and validation query-level metrics, ordered `candidate_trace` entries (stable candidate ID, settings, train and validation metrics), `selection` (`selected_candidate_id` and reason), corpus/index UUID and mapping fingerprint when available, effective filters, algorithm version, `tuning_budget`, and any incomplete/stop state. Runs remain owner-scoped and immutable.
- `validation_diagnostics` compare baseline and selected validation results per query. Show query-level metric deltas, known-relevant documents newly missed or recovered at the fixed cutoff, retrieved-unjudged counts, stale-judgment counts, and incomplete/error categories. Call them “known-relevant judged targets”; do not treat absent or explicit-unjudged qrels as nonrelevant or claim exhaustive misses when judgments are incomplete.
- Do not overwrite the stored concept settings automatically. A returned candidate is an experiment recommendation; applying it remains an explicit user action through the existing workflow.

## Fixed response contract

- `candidate_trace` is ordered and bounded by `max_candidates`. The saved baseline uses candidate ID `baseline`; later IDs are `candidate-001`, `candidate-002`, and so on. Each entry exposes `settings`, `train_metrics`, `validation_metrics`, and `evaluation_status`.
- `selection.selected_candidate_id` is `baseline` or a candidate ID. `selection.reason` is one of `candidate_selected`, `no_candidate_improved`, `baseline_retained_tie`, `validation_unavailable`, or `validation_failed`.
- `validation_diagnostics` is a list with one entry per validation query. Entries expose `query_id`, `query`, `status`, `metric_deltas` (`ndcg_at_k`, `judged_coverage_at_k`, `recall_of_judged_relevant_at_k`), `baseline_missed_known_relevant`, `selected_missed_known_relevant`, `missed_relevant_added` (newly missed targets), `missed_relevant_fixed` (recovered targets), baseline and selected retrieved-unjudged counts, stale-judgment count, and safe incomplete/error categories. Missed-target records include the concrete document index, ID, and stored rating when available.
- `tuning_budget.candidates_evaluated` counts candidate configurations for which train evaluation completed, including a candidate whose validation evaluation later reached the time limit. `elapsed_ms` records the run duration and `stop_reason` reports `completed`, `candidate_budget`, or `time_budget`.
