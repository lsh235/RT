# Cycle 19 information-need visibility navigation acceptance

## Scope and baseline

- Baseline supplied for this cycle: `v0.16.0`, commit `50e16dc109ed77fca187dc15cdeddcdb71af1ee9`.
- Requested implementation and QA override: `gpt-6-luna`; runtime identity is **UNVERIFIED** because no task telemetry proves the executing model.
- Scope: keyboard-usable links from each repeated-document occurrence to the successful query card containing that result. Card IDs are generated from successful result position; query IDs remain exact card/link metadata. Query grading controls stay associated with their query. No backend, API, database, or provider changes are part of this UI acceptance.
- Interpretation boundaries reuse the [Cycle 18 visibility acceptance](cycle18-information-need-visibility-acceptance.md) and the [Cycle 11 research record](cycle11-evaluation-pool-vs-query-groups-research-2026-10-18.md), checked 2026-10-18. Cycle 11's [Elastic ranking evaluation guide](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval) and [NIST TREC relevance-judgment guidance](https://trec.nist.gov/data/reljudge_eng.html) support keeping query-specific evidence and not treating unobserved documents as negative judgments. Linking an occurrence to its exact query card is a **product navigation inference**; it makes no retrieval-quality or relevance claim.
- The two unrelated user documents `docs/agent-sdk-upstream-review-2026-10-18.md` and `docs/novice-retrieval-improvements-2026-10-18.md` were left untouched. The fixture intercepts all `/api/**` calls and supplies synthetic data. No live Elasticsearch, user database, corpus, credentials, or embedding/provider service was accessed.

## Iteration notes

- An early browser launch was attempted before the static server had started and returned `net::ERR_CONNECTION_REFUSED`; starting the server first resolved it.
- The first card-grade assertion expected one control per card, but cards correctly contained several document controls, all carrying the same exact query ID. The assertion was corrected to require one or more controls and verify every control matches its card.
- The first partial-failure fixture had only one successful query, so no repeated document existed to carry a link. The fixture now has three query variants: two succeed and share repeated documents while the hostile-ID query fails; links are checked against the two successful cards and excluded for the failure.
- All final gates above passed after those fixture corrections. No product failure remained open.
