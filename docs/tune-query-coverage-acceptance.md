## Acceptance criteria

| Gate | PASS when | FAIL when |
|---|---|---|
| Distinct query aggregates | Existing document counts and eligibility remain unchanged. Total query counts include unlabeled query entries in each split of the submitted concept; graded and positive query counts deduplicate query IDs, even with multiple judgments in one query. Unsaved query-list edits can change these denominators. | Queries are counted per judgment/document, or unlabeled request query entries disappear from denominators. |
| Judgment selection | Positive validation labels do not enable tuning. Stale rows only increase `stale`; grade 0 and null/pin-only do not count positive; a pinned row with a real positive rating still counts. | Any stale/validation/pin-only row changes training eligibility or split aggregates incorrectly. |
| Privacy and read-only behavior | Response remains aggregate-only with no Elasticsearch request or connection data, and normal readiness reads leave persisted judgment/concept/version/run rows unchanged. Missing, malformed, empty, and legacy schemas remain covered; byte-for-byte equality is checked for empty/malformed store fixtures. | IDs/reasons leak, persisted state or tested fixture bytes change, or a read causes an Elasticsearch call. |
| UI wording and races | UI renders plain Korean query numerator/denominator for train and validation, distinguishes graded and positive query coverage, explains it reflects the current query list (which may include unsaved edits), says counts do not establish representativeness or quality and imposes no arbitrary minimum; late split-edit responses and 503 errors remain safe. | UI omits query coverage/caveats, displays an obsolete response after edits, or promises quality/tune success. |
| Regression/package | Focused and full suites, disposable browser smoke, syntax/whitespace checks, and isolated exact `0.7.0` wheel install/CLI pass on final source. | A required gate fails without a fix and rerun, or NOT RUN is represented as PASS. |

## Fixture scope

`tests/test_concept_tune_readiness.py` uses only temporary SQLite databases and a dynamic loopback port. It adds synthetic train/validation queries, multiple judgments within a query, positives across multiple query IDs, unlabeled queries in both splits, and assertions for distinct query coverage while preserving existing readiness gates. The browser fixture in `tests/run_tune_readiness_fixture.py` is synthetic and uses a dynamic port. No user database, credentials, or ports 8765/8766 are used.
